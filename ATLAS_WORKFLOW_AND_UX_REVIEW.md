# ATLAS Workflow and UX Review

**Method note:** No browser-automation tool was available in this environment. Everything below is derived from reading the actual component source — what state each page reads/writes, what a click handler does, what the save/navigation code path is — cross-checked in several places against live API behavior. Claims about literal visual rendering (spacing, color, pixel layout) are not made; claims about *behavior* (does the button save, does the value persist, is the completion state honest) are code-verified and are the substance of this report, consistent with the review brief's instruction to verify behavior over appearance.

## 1. Cross-page state integrity

ATLAS currently has **three coexisting persistence mechanisms** feeding the workflow UI, not one:
1. `localStorage` node-state (`atlas-workflow-node-state:<projectId>:<stepId>`), read/written directly by `WorkflowPlaceholderStep.tsx`.
2. A newer SQLite-backed persistence API (`/api/projects/{id}/workflow-state`, `server/persistence/persistence_router.py`).
3. The legacy JSON-registry project/ACL system (`server/projects/project_router.py`).

This matches the architectural finding in the security review (FND-002): there is no single, obviously-authoritative place workflow progress lives. A user's "page complete" state can, in principle, exist in the browser and not the server, or the server and not the browser, depending on which write path a given page uses and whether that write succeeded (see the A/B Testing findings below for a concrete instance of exactly this class of bug, and the fix applied to it earlier in this engagement). This is the single most important cross-cutting UX risk: **users cannot fully trust that "complete" means "saved,"** because the codebase itself doesn't have one save path.

## 2. Predictive Modeling workflow (Step00–Step13)

Reviewed via `src/steps/Step00_ProjectContext.tsx` through `Step13_ModelMonitoring.tsx`, `src/config/workflows.ts` (`predictiveModelingSteps`), and the corresponding backend routers (`training`, `evaluation`, `splitting`, `preprocessing`, `model_diagnostics`, `model_documentation`, `scoring`).

This is the most mature and complete workflow in the platform. Each step has a real backend endpoint behind it (not a stub), the routers are gated by `Depends(require_user)` (per the `assert_api_routes_authenticated` guard confirmed passing), and downstream steps genuinely consume upstream artifacts (e.g., the evaluation step reads the training step's stored model artifact via `RESULTS` rather than recomputing). Session state for the active predictive-modeling run is held in an **in-memory singleton (`DATASTORE`/`RESULTS`)**, not per-user/per-project scoping — this is a real architectural constraint (flagged previously in this engagement, not re-verified live in this pass): two users training models concurrently on the same backend process would interfere with each other's session state. For a single local user this is invisible; it is a hard blocker the moment more than one person uses the same backend process at once.

**TRAIN/TEST/OOT role discipline:** the `atlas_split` convention (a split-indicator column produced by the Balance & Split step) is correctly excluded from the feature set in the credit-risk ML engine (verified this pass — see workflow report companion finding) and is documented as a reserved column. Preprocessing fit-then-transform discipline (fit only on TRAIN) was reviewed in an earlier pass of this engagement for the credit-risk WOE/IV and scorecard engines and found correct; it was not independently re-verified for every step of the generic Predictive Modeling pipeline in this pass — recommend a dedicated leakage-focused pass across `server/preprocessing/`, `server/splitting/`, and `server/training/` before relying on this workflow for a real model that will be validated.

**Completion gates:** `StepShell.tsx`'s `handleNext` does mark the step complete and persist before navigating, and shows a visible error banner on failure rather than failing silently — this is a sound, honest pattern (contrast with the A/B Testing bug below, which used a *different* handler that did not have this property until fixed this session).

## 3. A/B Testing workflow — reviewed in depth this engagement, including a live defect fix

This workflow's "Mark Complete & Next Step" button was reported broken by the user earlier in this engagement and root-caused and fixed as part of this same review effort (not merely observed — actually diagnosed and repaired, then verified against the test suite). Recorded here for completeness of the workflow audit trail:

- **Root cause:** the button's save handler (`handleAbTestingMarkCompleteAndNext` in `src/steps/WorkflowPlaceholderStep.tsx`) treated the browser `localStorage` write as mandatory: if `saveAbTestingStep()` returned `browserCacheWritten: false` (which happens whenever `localStorage.setItem` throws, most commonly `QuotaExceededError`), the handler threw before ever calling `navigate()`. Storage quota was typically exhausted by *unrelated* large keys (other workflows' node state, full project snapshots) — not by A/B Testing's own data — so pruning logic scoped only to A/B keys never freed the space that was actually full, which is why repeated attempts at fixing this by scoping cache-pruning to A/B-prefixed keys never resolved it.
- **Fix applied:** the save is now best-effort inside try/catch, retries once via a broader `reclaimWorkflowStorage()` sweep (all oversized workflow keys, not just A/B), and **navigation now always proceeds** regardless of whether the local cache write ultimately succeeded — with a non-blocking amber notice shown if it didn't, rather than a dead button.
- **Also fixed this engagement:** the Project Context page previously displayed the demo dataset (`AB_MARKETING.csv`) and its column mappings as if already confirmed, before the user had completed Data Acquisition. This is now gated behind a computed `abTestingDataAcquisitionConfirmed` flag (true only once the "Data Acquisition" step is marked complete) and the UI now reads "Suggested dataset" / "Dataset not confirmed" until that gate passes.
- **Verification performed:** `npx tsc -b` (clean), and the `experimentation`, `persistence`, `regression`, and `workflowNavigationState` test suites (all passing after two brittle source-string assertions were updated to match the corrected, equivalent behavior rather than a literal string that was intentionally changed). **Not verified via an actual browser click-through** in this session (no browser tool available) — the user should still run the manual QA sequence (type text, click, confirm navigation, refresh, confirm persistence) before treating this as fully closed.

This is flagged as a **pattern to look for elsewhere**: any other workflow whose save handler throws on a `localStorage` write failure before calling `navigate()` has the same latent bug. A quick grep for `browserCacheWritten` / `throw` patterns in the remaining workflow step files is recommended.

## 4. Credit Risk Studio

Reviewed in depth in an earlier pass of this engagement (server-side leakage guard for `RiskPerformance`/`bad_flag`/`atlas_split`, full-dataset enforcement) and re-checked this pass:

- **Full-dataset enforcement is now correct** (FND-006, positive): `woe_iv_engine.py` and `scorecard_engine.py` both require `data_full.csv` and hard-block (409) if only a sample is available.
- **`atlas_split` is now respected for train/validation partitioning** in `ml_engine.py` (checked this pass, L133-149): if an `atlas_split` column is present it is used to partition data; `train_test_split` is only used as a fallback when no such column exists. This closes a leakage/discipline gap flagged in an earlier pass.
- **Architecturally, Credit Risk Studio remains a parallel system, not a wrapper around Predictive Modeling.** No shared `modeling_core` (or equivalent) module was found; `server/credit_risk/ml_engine.py` still implements its own data loading and splitting rather than delegating to `server/training/` or `server/splitting/`. This was flagged as an architectural recommendation in an earlier pass of this engagement and remains open — it is a **Large/Architectural** item, not a quick fix, and its absence means any future leakage-guard or full-dataset fix has to be applied twice (once for Predictive Modeling, once for Credit Risk Studio) rather than once in a shared place. The two fixes above (full-dataset, `atlas_split`) are evidence this is being done correctly but manually, which is exactly the maintenance cost the architectural recommendation was meant to avoid.

## 5. Placeholder/generic workflows — Reinforcement Learning, Computer Vision, Graph Analytics (FND-007)

These three project types render `workflows.ts`'s domain-specific step *labels* ("Entity and Edge Definition," "Annotation Strategy," "Environment Definition") through the fully generic `WorkflowPlaceholderStep.tsx` form — the same "Objective / Inputs / Assumptions / Method / Metrics / Risks / Decision / Rationale / Notes" text-box set used for every unbranched project type, with no domain tooling behind any of them. The one differentiator per type is a short, genuinely well-written "Atlas Guide" bullet list (e.g., for Graph Analytics: "Define nodes, edges, direction, weights, and time validity before modeling. Validate graph features for leakage and investigation usefulness.") — good, specific guidance text, attached to a form that cannot act on any of it. This is the clearest instance in the platform of a workflow that *reads* as complete (a full multi-step navigation structure with sensible-sounding labels) but *is* a shell. It should not be presented to a prospect or pilot customer as equivalent in depth to Predictive Modeling, Credit Risk Studio, A/B Testing, Optimization, or Time Series.

## 6. Optimization, Time Series & Forecasting, LLM/Generative AI

Unlike the three above, these have dedicated frontend implementations (`src/features/optimization/`, `src/workflows/time-series/`, `src/features/llm/`) and connect to real backend computation:
- **Optimization** has a substantial backend (`server/optimization/`: solver service, sensitivity analysis, scenario service, a transportation-problem template, codegen, and evidence capture — 10 files) with a dedicated `TransportationOptimizationWorkflow.tsx` and `OptimizationWorkflowStep.tsx` frontend. This is a real, non-trivial implementation, not a shell — depth of the actual solver logic (feasibility handling, shadow prices, robust optimization) was not independently re-derived line-by-line in this pass.
- **Time Series & Forecasting** and the broader **Analytics/Statistical Engine** (`server/analytics_engine/`) were spot-checked this pass: `classification.py`'s diagnostics module computes real ROC/PR-AUC/KS/calibration/decile statistics via `sklearn`, from a dataframe sourced through `dataset_adapter.load_dataset()`, which — importantly — **refuses to run on anything but the full governed dataset artifact** (raises `InsufficientDataError` if `data_full.csv` is missing), the correct pattern the credit-risk engines have now also adopted. This is a genuine strength: real statistics, computed on governed data, not fabricated or sample-derived.
- **LLM/Generative AI** workflow depth was inventoried (directory exists, connected via `src/api/analyticsEngine.ts`'s `llm_evaluation` endpoint) but not read function-by-function in this pass. Flag for a dedicated follow-up: specifically verify whether generated narrative can be saved into Model Documentation Studio as "complete" without an explicit human-review/acceptance step, per the review brief's specific concern about AI-generated language being silently treated as approved documentation.

## 7. Navigation, terminology, and guidance quality

- Terminology is largely consistent and domain-appropriate (WOE/IV, PDO scaling, KS, decile analysis, IV ranking used correctly and matched to the credit-risk domain; "atlas_split"/"bad_flag"/target-label exclusion language is precise and matches how a model-risk reviewer would expect to see it named).
- The per-project-type "Atlas Guide" sidebar content (`recommendations()` in `WorkflowPlaceholderStep.tsx`) is genuinely good, specific guidance — not generic filler — for every project type including the three placeholder ones (§5). This is a case where the *guidance* was clearly written by someone who understands each domain, even where the *tooling* to act on that guidance doesn't yet exist.
- The dataset-defaults-shown-as-confirmed pattern fixed in A/B Testing this engagement (§3) is worth auditing across other workflows for the same "suggested vs. confirmed" ambiguity — it is a plausible pattern to recur anywhere a workflow shows demo-dataset defaults before Data Acquisition is complete.

## 8. Recommended workflow-level changes

1. Pick one persistence mechanism for workflow/step state (see FND-002/§1) and migrate the others, rather than maintaining three.
2. Audit every workflow's "Mark Complete & Next" handler for the throw-before-navigate pattern found and fixed in A/B Testing (§3).
3. Either build minimal real tooling for Reinforcement Learning, Computer Vision, and Graph Analytics, or visibly mark them "Early Access / Generic Workflow" so they are not mistaken for equivalent-depth offerings (§5).
4. Migrate Credit Risk Studio onto shared modeling primitives rather than continuing to hand-port each leakage/discipline fix into its private engines (§4) — Large/Architectural, but the maintenance cost of not doing this is already visible in the fact that the same two fixes had to be applied twice.
5. Run the manual browser QA sequence for the A/B Testing fix (§3) since this review could not execute it directly.
