# Query Contract, Sampling, Security, Audit, and Wide-Table Guide

Source of truth: `server/analytics/query_contract.py`, `sampling.py`, `artifact_resolver.py`, `resource_governance.py`, `engines/polars_engine.py`.

## Query contract

`AnalyticalQueryRequest` (client-supplied) deliberately has **no `userId` field** — the authenticated user is always resolved server-side via `require_user`/`active_user()`, exactly like every other ATLAS endpoint. `queryId` is server-generated by default (`new_query_id()`); a client may supply `clientRequestId` for its own correlation, which is never trusted as an identity or authorization signal.

`AnalyticalQueryResponse` always states whether a result is `exact`/`approximate`/`sampled`/`pushdownApplied`/`cacheStatus`, plus `sourceRowCount` vs `resultRowCount` vs `rowsScanned` — a client can always tell "this is everything" from "this is a summary of everything" from "this is a sample."

`CONTRACT_VERSION = "1.0"` is included in every response (`AnalyticalQueryResponse.contractVersion`) so a future breaking change to the response shape is detectable by clients.

## Sampling and approximation policy

Implemented in `server/analytics/sampling.py`:

- **`random_sample`** — uniform, seeded (`numpy.random.default_rng(seed)`).
- **`class_stratified_sample`** — preserves each class's share of the sample; a minority class is never silently dropped by a plain random draw.
- **`target_band_stratified_sample`** — bins the regression target into quantile bands and samples proportionally from each, preserving the target's distribution shape (not just its mean).
- **`reservoir_sample`** — used when the total population size may not be known in advance.
- **`top_n_by_metric`** — authorized bounded rows ranked by a metric (e.g. largest residuals).
- **`hexbin_density`** — returns bin centers + counts, never raw points, for scatter data that would otherwise exceed the bounded-point limit.
- **`approximate_quantiles`** vs **`exact_quantiles`** — both implemented; the response always labels which was used (`AnalyticalQueryResponse.exact`), and DuckDB's `APPROX_QUANTILE`/`QUANTILE_CONT` mirror the same exact/approximate split server-side for file-backed sources.

**Determinism:** every sampling function accepts an explicit seed and is deterministic given one (verified directly against the 1M-row fixture: two identical `bounded_sql_sample` calls with the same seed returned identical rows — see Performance Report).

## Query security

`server/analytics/artifact_resolver.py` is the **only** place a query's data source is resolved to a file path or in-memory frame:

1. **No client-supplied paths.** A request only ever carries `projectId`/`datasetId`/`versionId`/`sourceType` — never a path. The resolver derives the path itself from the Dataset Library registry.
2. **No client-supplied ownership.** Every branch calls an existing ATLAS authorization function (`authorize_modeling_scope`, `require_dataset`) that resolves identity from the session, not from the request body.
3. **Path traversal prevention.** `_within_artifact_root()` resolves the candidate path to an absolute path and verifies it is inside `ARTIFACT_ROOT` before any file is opened — verified by a dedicated test.
4. **No arbitrary SQL.** Visualization clients send a typed `operation` + typed parameters (`selectedColumns`, `filters`, `groupBy`, `aggregations`) — never raw SQL text. `duckdb_engine.py` builds parameterized SQL internally; user-controlled *values* are always bound via `conn.execute(sql, params)`, never string-concatenated.
5. **Identifier safety.** Column/group-by identifiers are validated against `_IDENTIFIER_SAFE` (alphanumeric/space/underscore/hyphen/period only) and double-quote-escaped before being interpolated as SQL identifiers (the one place SQL doesn't support parameter binding).
6. **Denied requests are audited.** Every `resolve_source()` failure and every 403 from the router calls `audit_event("access.denied", ...)`.
7. **Cache obeys the same boundary.** `result_cache.py`'s cache key includes the resolved user scope and project id, and `get()` double-checks the stored entry's owner/project match before returning it — even though the key itself is already scoped.
8. **Project deletion invalidates.** `persistence_router.py`'s `delete_project` calls `RESULT_CACHE.invalidate_project()` and releases that project's concurrency counters.

## Query audit

Every execution and denial calls the existing `audit_event()` (`server/security/security_store.py`) with `queryId`, operation, engine, pushdown, exact/approximate, sample method, duration, cache status, dataset/version identity — **never raw row values**. The `GET /api/analytics/diagnostics/planner` endpoint (mirrors the existing `/api/system/diagnostics` pattern) surfaces the decision matrix, live resource limits, configured distributed engines, live concurrency counters, and cache stats for development inspection.

## Wide-table strategy

Verified against 500-column and 1,000-column fixtures (see Performance Report):

- **Lazy schema retrieval** via Polars (`get_schema_paginated`) — never returns all columns by default; server-side `offset`/`limit` pagination, `search` (substring match on column name), `dtype_filter`.
- **Profile-on-demand**, two modes: `lightweight_column_profile` (null count + dtype, cheap) and `deep_column_profile` (full numeric summary, more expensive) — no automatic profiling of all columns at page load.
- **`top_feature_summary`** — bounded (default 20 columns) null-count-ranked summary, so a 1,000-column table never triggers 1,000 profile computations in one call.
- **Column selection limits** — `resource_governance.LIMITS.max_selected_columns` (default 50) is enforced by the planner for every non-schema operation.

**Not built this phase:** server-side sorting of feature metadata by arbitrary computed statistics (only null-count ranking exists via `top_feature_summary`); background profiling with cancellation for whole-table deep profiles. Both are reasonable Phase 2 extensions of the same Polars lazy-scan foundation.
